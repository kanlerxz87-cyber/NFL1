# Official injury-data publication policy audit

**Reviewed:** 2026-11-15 (UTC)
**Repository state audited:** `main` at `df084b5` (the base of `arena/48ab654c-nfl1`)
**Scope:** NFL.com injury-report terms, the current repository's collection and publication paths, and the policy gate needed before adding more snapshots.
**Boundary:** This is a source-text and repository audit, **not legal advice**. It does not determine whether any particular use is lawful, whether an external permission exists, or what a court would decide.

## Executive finding

The current [NFL.com Terms and Conditions](https://www.nfl.com/legal/terms/) say that systematic retrieval to create or compile a collection is prohibited without the NFL's express prior written consent (§1.3). Section 1.1 separately restricts copying, reproducing, distributing, displaying, and transmitting Services content except as the Agreement expressly permits. The repository currently has an automated NFL.com injury-report fetch, stores player-level report rows in tracked files, and publishes row-level copies on its public GitHub Pages site. The repository is public, and Pages is configured to build from `main` at `/`.

That is a **material, unresolved source-terms/permission risk**. It is not resolved by adding a source citation to each row, retaining only a hash of the raw HTML, calling the work non-commercial, or publishing only a derived page after the same systematic collection. The terms' application to particular derived outputs still needs qualified review; this report does not make that legal determination.

I found no written-permission record in the tracked repository. That does **not** prove that permission does not exist outside the repository. No injury data, scraper, workflow, or published page was changed in this audit. PR [#68](https://github.com/kanlerxz87-cyber/NFL1/pull/68) merged at 2026-11-15T12:48:28Z; it added the six-hour snapshot workflow and F51. After the merge, the live ledger showed four scheduled reads, one public 347-row capture, and no recorded field deltas; the live root [Flagged for Review page](https://kanlerxz87-cyber.github.io/NFL1/flagged.html) now includes F51. The merge did not resolve the permission question. The follow-up request is to keep the capture paused or behind a documented permission/source-policy gate until that question is cleared.

## Suggested decision paths

These are project recommendations, not legal findings.

1. **Permission-first (preferred if immutable injury history is required).** Request written permission from the relevant rights holder. The request should identify the exact endpoint; fetch cadence; fields; raw/parsed retention; immutable historical captures; row-level/public publication; derived metrics; attribution; hosting; intended competition/rewards; territory; and duration. Attach the grant and a review date to a source-policy register.
2. **Licensed-source path.** If permission is unavailable, choose a source whose published licence or contract expressly allows the intended collection, archiving, backtesting, and publication. Verify the licence independently for every source; do not transfer a licence from one feed to a different publisher.
3. **Fail-closed while unresolved.** Do not add or enable new automated NFL.com captures or expose new raw rows until path 1 or 2 is cleared. Keep the official source link and clearly labelled unknowns; do not treat blanks as availability. An authorized owner should separately decide how to handle current public copies and the Git history—no history rewrite was attempted here.

### Recommended engineering gate

Before any NFL.com request is made, the collector should require a reviewed source-policy record that includes the exact permission/licence reference and scope. If it is absent, expired, or does not cover the requested endpoint, frequency, retention, and publication plan, fail closed before fetching. A “terms reviewed” checkbox, a citation beside each row, a raw-response hash, or storage outside the website is not by itself an authorization record.

If no permission or source with suitable rights is established, injury features should remain unavailable rather than being populated from unapproved captures. This is consistent with the project's rule to leave unsupported values blank and flag the blocker.
