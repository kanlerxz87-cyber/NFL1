## What counts as a registration

A registration is a git commit that contains, and contains only, the **definition** of
something to be evaluated later:

1. the rule text (what bet, if any, is placed and when),
2. the sample window (which games, which seasons, which prices),
3. the gates (what result would make the claim believable), and
4. the two-sided mind-changer field: `upside` (what would change our mind *towards*
   believing the edge is real) and `downside` (what would change our mind *against* it).

The **commit hash of that commit is the registration**. A later commit may record that
hash; it may not change the definition.

## Registration kinds (honest labelling)

| kind | meaning | may claim pre-registration? |
|---|---|---|
| `prospective` | The registration commit precedes every forecast and every result of the entry. | yes |
| `prospective-eligible` | The entry has never been evaluated anywhere in this repository. Registration now precedes its *first* evaluation; the first evaluation must cite the registration hash. | yes, from now on |
| `retrospective` | Rules and results already existed together in the repository before this registry (flag R26-01 pattern: same commit, or same session). Registered now **for disclosure only**. | **no** — ever |

A retrospective entry never becomes prospective. It can only be superseded by a new,
frozen, re-written rule under a new id.

## Sample-window and holdout policy

The frozen corpus is `data/prereg/corpus.json` (PR-09). It defines three disjoint splits
(train / validation / holdout). **Holdout seasons (2025–2026) may not be reported on for
any registered entry until a recorded decision opens them** in `data/prereg/corpus.json`
(`holdout_opened`). Any number published from the holdout before that record exists is a
gate violation, not a result.

Every evaluation run of a registered entry must state which corpus version it scored on.

## Leaderboard policy (PR-06)

* The **prospective board** (`prereg/registry.html`) lists only entries whose registration
  hash precedes their forecasts, and shows numbers only after those forecasts settle.
* The **backtest archive** (`prereg/archive.html`) may show historical numbers, always
  labelled retrospective. It is an archive, not a leaderboard: no ranks, no rewards, no
  "top strategy" language — the brief forbids backtest numbers from appearing on the
  leaderboard.
* **Controls (PR-17)** — a random-side control and a favourites-only control — are
  registered alongside every board run so a lucky run can be compared against no-skill.

## Forecast policy (PR-18)

A forecast record must contain: the registration hash, the input file's sha256 at record
time, a `recorded_at` timestamp **earlier than every kickoff it covers**, and the
aggregates needed to reproduce every probability. `prereg/verify.py` recomputes the
probabilities from the recorded aggregates and fails if any `recorded_at` is not earlier
than its kickoff.
