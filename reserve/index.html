Official transactions and reserve list

Dated roster events from the league's own transactions register — trades, signings, reserve lists, waivers, terminations — captured with a timestamp and a hash, joined to the official weekly injury report so that “not listed” is never read as “available”.

Why this page exists: the weekly injury report and the reserve list are two different official records. A player on injured reserve is not on the weekly report at all, so a count taken from the report alone understates who a club cannot play. This is the league’s own dated register of those moves — captured, hashed, and replayable.

The printed cap: the source shows at most 25 rows per category-and-month page. The league's month page prints at most 25 rows, newest first, and offers no deeper window (`?page=2` repeats the same rows; a per-day url returns 404). A page at 25 rows is therefore only complete for the month if its oldest printed row is on the first day. Capturing the running page often is what recovers the rest: the derived register is the union of every capture of that page, so a row is never lost by leaving the printed window. 15 page(s) sit at that cap; 15 of them are incomplete at the source for their month (the oldest row printed is later than the first of the month), which is a limit of the league’s page and not a gap in this capture. Rows are recovered by reading the running page repeatedly: the register below is the union of every read, so a row never disappears when it slides out of the printed window. Every capped page is in the month still being captured, so the sweep completes it.

A month that was never fetched is absent from this table rather than shown as zero: absence is a gap in our capture, zero is a claim about the league. The pinned category and month list lives in pipeline/collect_transactions.py.

Method, and what this cannot say

  • Source. www.nfl.com/transactions/, the league's own register, six categories by month. It is the same host as the injury report; no third-party odds or news-aggregator data is used here.
  • Capture. The fetcher records the UTC time, the HTTP status, the byte count and the SHA-256 of the raw page, then parses each table by header name, never by column position. A capture file is written only when the parsed content changes, with exclusive-create, so history is append-only and a replay is possible.
  • Blank is blank. The Position column on these pages is usually empty. It is stored empty and printed as not printed: 0 of 484 rows carry a printed position. No position is inferred from the player's club roster.
  • Club codes. The register prints AZ for Arizona and LA for the Rams; the repository uses ARI and LA. The printed code is kept, and the mapping is recorded, because the same club appears under two codes in different official files (flag CAP-05 on the review page).
  • What it cannot say. It cannot say who the backup is, which depth slot a reserve move empties, or how much a return is worth: those need the depth chart and snap counts, and the league publishes neither in a form this repository can verify. It cannot be used as a price. It says only who moved, when, and to or from what list.
